คำว่า “ใช้ได้จริง” ในชุดนี้
เนื้อหาเขียนเป็นประโยคสำหรับรายงานแล้ว ไม่ใช่เพียงหัวข้อ แต่ยังต้องตรวจความตรงกับฉบับที่นำไปทดสอบและย้ายเข้าไฟล์ต้นฉบับ
ไฟล์ Word เป็นชุดเนื้อหาปรับปรุง ไม่ใช่เล่มสมบูรณ์ที่รวมส่วนเดิมทุกหน้า ไม่ได้แก้ PDF ต้นฉบับหรือใส่ลายเซ็น/ชื่อกรรมการแทนทีม
ข้อความกำกับสีฟ้าในวงเล็บเหลี่ยมเป็นคำสั่งสำหรับผู้เรียบเรียง ต้องนำออกก่อนส่งอาจารย์

2. เปลี่ยน Abstract ด้วยร่างใหม่ ตรวจชื่อผู้จัดทำ สังกัด ปี และอีเมลจากข้อมูลทีมจริง
3. ปรับบทที่ 1 ให้ตรงกับขอบเขตที่มีจริง เนื้อหาที่ให้มาครอบคลุม 1.1–1.7 โดย 1.5 ให้เติมตารางแผนงานและวันที่จริงเอง ไม่คัดลอกวันที่จากตัวอย่าง
4. บทที่ 2 เป็นเนื้อหาปรับปรุงเฉพาะส่วน ทฤษฎี/งานวิจัยเดิมที่ยังถูกต้องเก็บไว้ได้ ต้องตรวจ citation และข้อเปรียบเทียบแพลตฟอร์มอีกครั้ง
5. ปรับบทที่ 3 และเลขหัวข้อให้ตามตัวอย่าง: 3.1 Existing System, 3.2 New System, 3.3 Use Case Diagram, 3.4 Activity Diagram, 3.5 Sitemap, 3.6 UI Design, 3.7 Database Design

9. ตรวจ References ทั้งเล่มก่อนจัดหมายเลข เนื้อหาชุดนี้ใช้ [1]–[9] ตามรายการท้ายไฟล์ เลขอาจซ้ำรายการเดิม ต้องรวมและเรียงใหม่ให้ตรงทุก citation

ส่วนที่ยังเว้นไว้โดยตั้งใจ
- ผลทดสอบฟังก์ชัน: มีกรณีทดสอบแล้ว แต่ยังไม่มีผลการรันเพื่อเขียน Pass/Fail ในรายงานชุดนี้
- วิธีประเมินและผลจากผู้ทดสอบจริง: ยังไม่แต่งจำนวนผู้ทดสอบ เวลา คะแนน เปอร์เซ็นต์ หรือความคิดเห็น
- ภาพหน้าจอปัจจุบันและรูป Use Case / Activity / Sitemap / Database ที่ต้องปรับใหม่: มีแนวทางและคำอธิบาย แต่ยังต้องจัดทำภาพ
- วันที่แผนงาน ข้อมูลฮาร์ดแวร์ ลายเซ็น และข้อมูลผู้จัดทำที่ต้องยืนยันกับทีม

สิ่งสำคัญที่แก้จาก Proposal
- รายละเอียดเพิ่มเติม (notes) ไม่บังคับ แต่ description และข้อมูลหลักยังบังคับ ไม่ควรเขียนว่ารายละเอียดทุกช่องเป็น optional
- การแจ้งเตือนใกล้เคียงใช้ตำแหน่งที่เก็บไว้ รัศมีเริ่มต้น 2,000 เมตร และไม่ได้ใช้ AI จากประวัติงาน
- ไม่อ้างว่ามี Google Maps ปักหมุดหรือ GPS ติดตามสดที่ใช้งานแล้ว
- พื้นที่ศึกษารอบมหาวิทยาลัยกับเงื่อนไขบังคับ geofence เป็นคนละเรื่อง รหัสปัจจุบันไม่ใช่หลักฐานว่าบล็อกนอก 5 กิโลเมตรแล้ว
- อีเมลมหาวิทยาลัยไม่ใช่การตรวจสถานภาพนักศึกษากับทะเบียน
- สถานะเงินใน prototype / Stripe test mode ไม่ใช่หลักฐานการโอนเงินจริงหรือบริการ escrow ที่เปิดให้บริการแล้ว
- Public profile ไม่ควรเผยบัญชีธนาคาร และอีเมลติดต่อมีเงื่อนไขคู่จ้างงาน ไม่ใช่เปิดแก่ทุกคน
- โมเดลฐานข้อมูลเป็น MongoDB/Mongoose ใช้ ObjectId และ embedded document ไม่ใช่ VARCHAR/SQL foreign-key constraints
- แบบสำรวจความต้องการ 54 คนเป็นบริบทเดิม ไม่ใช่ผลประเมินระบบปัจจุบัน ต้องมีข้อมูลต้นทางหากจะอ้างเปอร์เซ็นต์
- การมีรีวิว moderation หรือ SOS ไม่ใช่ผลพิสูจน์ว่าป้องกันการโกงหรือรับประกันความปลอดภัยได้

วิธีใช้ CSV
เปิดผ่าน Excel ได้โดยไฟล์เป็น UTF-8 พร้อม BOM
Data Dictionary มีคำอธิบายว่างให้ทีมเติม เพราะส่วนนี้สร้างจาก schema โดยตรง ชื่อ field/type/enum/required/default/ref จึงอิงโค้ด แต่ไม่แต่งคำอธิบายรายฟิลด์ให้เหมือนเป็นนิยามทางธุรกิจที่ยืนยันแล้ว
required=false หมายถึง schema ไม่บังคับเอง ไม่ได้แปลว่า API หรือฟอร์มทุก flow จะยอมให้เว้นเสมอ ต้องตรวจ validation ของ flow ด้วย
excludedByDefault=true อธิบาย select:false ไม่ใช่กฎสิทธิ์ API ทั้งหมด
ก่อนแทรกกรณีทดสอบลงรายงาน ต้องระบุ application version/commit, สภาพแวดล้อม, payment mode, วันเวลา, อุปกรณ์/เบราว์เซอร์ และไฟล์หลักฐาน
ตัวอย่างหน้าจอและหลักฐานให้ใช้บัญชีสมมติ ปกปิดข้อมูลระบุตัวบุคคล และไม่ใส่ reset token, secret, API key หรือข้อมูลธนาคารจริง
