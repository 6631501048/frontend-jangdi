# ผลตรวจ bug หน้า JangDi

ตรวจโค้ด frontend เทียบกับ payload ที่ backend สร้างจริง แล้วตรวจการเรนเดอร์ การนำทาง การค้นหาที่คำตอบโหลดกลับมาสลับลำดับ สถานะอ่าน และข้อผิดพลาด API ด้วยข้อมูลจำลอง

## ปัญหาที่พบและแก้

| ส่วน | อาการก่อนแก้ | พฤติกรรมหลังแก้ |
| --- | --- | --- |
| Notification ผู้รับจ้าง | `ServicePost` อนุมัติ/ปฏิเสธบริการ และ `Payment` โหมด Demo ไม่มีหน้าปลายทาง | เปิดหน้าจัดการบริการ หรือหน้ารายการการเงินของผู้รับจ้างได้ |
| Notification งานใกล้ตัว | ไปหน้าติดตามงาน แม้ยังไม่ได้สมัครหรือได้รับเลือก | ไปหน้ารายละเอียดเพื่ออ่านและสมัครงาน |
| Notification ข้ามบทบาท | ปุ่มอาจส่งไปเส้นทางของอีกบทบาท แล้ว route guard พากลับหน้าแรก ทำให้เหมือนกดไม่ทำงาน | ตรวจเจ้าของงาน/ผู้รับงานและบทบาทก่อนนำทาง อธิบายให้สลับบทบาท และยังไม่เปลี่ยนเป็นอ่านแล้ว |
| Notification โหลดรายละเอียดล้มเหลว | อาจเปลี่ยนเป็นอ่านแล้วทั้งที่ยังเปิดหน้าปลายทางไม่ได้ | คงแผงและสถานะยังไม่อ่านไว้ ให้ลองกดใหม่ได้ |
| Notification เรียลไทม์ | คำตอบ refresh เก่าอาจทับข้อความ socket ใหม่ หรือทำให้รายการที่เพิ่งอ่านกลับเป็นยังไม่อ่าน | รวมรายการใหม่และสถานะอ่านที่เปลี่ยนระหว่างโหลดก่อนอัปเดต store |
| Notification หลังออกจากระบบ | คำตอบ read/read-all ที่ค้างจาก session เก่าอาจแก้สถานะของ session ใหม่ | ตรวจ session version ก่อนอัปเดตสถานะ |
| รายละเอียดงาน/บริการ | เปลี่ยน ID แต่ใช้ component เดิม อาจยังแสดงข้อมูล ID ก่อนหน้าจนกว่าจะโหลดใหม่/ถึงรอบ polling | ผูก component ของ RouterView กับ path เพื่อโหลดข้อมูลใหม่ทันที |
| งานของฉันฝั่งผู้รับจ้าง | URL เปลี่ยน `view=services` แต่แท็บยังอยู่ที่งานที่สมัคร | ตาม query ทั้งไปและกลับได้ |
| ค้นหาฟีดทั้งสองบทบาท | คำตอบจากคำค้นเก่าที่กลับมาช้าทับผลคำค้นล่าสุด | รับผลเฉพาะคำขอล่าสุด และไม่ให้ polling แทรกคำขอค้นหาที่ยังโหลด |
| โปรไฟล์ | ตั้ง error ในโค้ดแต่ไม่ได้แสดงบนหน้า ทำให้โหลด/บันทึกไม่สำเร็จโดยไม่เห็นสาเหตุ | แสดงข้อความผิดพลาด ลองโหลดใหม่ได้ คงฟอร์มที่บันทึกไม่สำเร็จ และไม่ให้เริ่มแก้ข้อมูลว่างก่อนโหลดโปรไฟล์สำเร็จ |

เส้นทางแจ้งเตือน Payment เก่าไปหน้ารายการการเงิน เพราะ backend ส่ง Payment ID ไม่ใช่ Job ID; ไม่มีการเดา Job ID หรือสร้าง endpoint ใหม่ ไม่ได้สลับบทบาทหรือทำรายการเงินให้ผู้ใช้อัตโนมัติ

## ขอบเขตการตรวจแต่ละหน้า

ตรวจ 43 กรณีเส้นทาง ครอบคลุม authentication, ผู้ว่าจ้าง, ผู้รับจ้าง, รายละเอียด/คำขอ/ฟอร์มประกาศ, การเงิน, โปรไฟล์, ประวัติ, รีวิว, แจ้งเตือน และแอดมิน ที่ 320/390/768/1440px รวม 172 การจัดวาง

- [ผลตรวจรายหน้า](ui-review/all-pages/checks.json): ไม่พบ runtime exception หรือแนวนอนล้นในกรณีที่ตรวจ
- [11 กรณี bug ที่ตรวจซ้ำ](ui-review/bug-audit/regressions.json): notification จาก payload จริง, ข้ามบทบาท, โหลดผิดพลาด, เปลี่ยนงาน, query, ค้นหาช้า และโปรไฟล์
- [18 กรณี notification UI](ui-review/notifications/checks.json): popover/sheet, keyboard, read/read-all, error/retry การรับรายการใหม่ และตำแหน่ง badge 32 รายการของทั้งสองบทบาท
- [13 กรณีฟอร์ม/คีย์บอร์ด](ui-review/all-pages/interactions.json): ฟอร์มหลายขั้นตอน การคืน focus และการใช้งานปุ่ม
- `npm test`: 74 รายการผ่าน รวม regression ที่ก่อนแก้ล้มเหลวใน routing และ notification refresh
- `npm run build`: ผ่าน

รันซ้ำโดยเปิด Vite ที่ `127.0.0.1:5175` แล้วใช้ `node scripts/check-bug-regressions.cjs` สำหรับกรณี bug หรือใช้สคริปต์ตรวจ UI ที่ระบุในเอกสาร design system

## ข้อจำกัด

การตรวจเบราว์เซอร์ใช้ Chrome profile และ API fixture แยก ไม่ทำรายการบัญชี งาน หรือเงินจริง ไม่ได้ยืนยัน Google OAuth, Stripe จริง หรือการส่ง socket จาก server จริง การผ่านชุดตรวจเหล่านี้ไม่ยืนยันว่าไม่มี bug ในทุกข้อมูลและทุกสถานะ

ได้รับภาพหน้า `/worker/feed` ซึ่งกระดิ่งเป็นสีดำทึบและเลข 32 เป็นลิงก์หลุดลงใต้ header แล้ว รูปมีลักษณะของ RouterLink เดิมที่ไม่ได้รับสไตล์ แต่การโหลดใหม่จากเซิร์ฟเวอร์ `localhost:5173` ให้ NotificationBell แบบ button และแสดงผลถูกต้อง จึงสงสัยหน้าเดิมค้างระหว่าง HMR ยังยืนยันสาเหตุในแท็บเดิมไม่ได้

เพิ่ม SVG presentation attributes เพื่อกำหนดขนาด 22px และเส้นกระดิ่งโดยตรง พร้อมตรวจ computed style และตำแหน่ง badge ของ worker/hirer ที่ 320, 390 และ 1440px บน localhost:5173 ด้วยข้อมูลจำลอง 32 รายการ ผ่านทั้ง 6 แบบ รวมการเปิด/ปิด preview ภาพตรวจ: [worker desktop](ui-review/notifications/worker-feed-count32-1440.png), [worker mobile](ui-review/notifications/worker-feed-count32-390.png) การ build ผ่าน
